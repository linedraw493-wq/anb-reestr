# Реестр блогеров — вопросы и дыры перед стартом

Свод из сессии 01.09.2026 (Даня читал спеку `speka-nedelya-1.pdf` вместе с
Котом). **Это не билд.** Слово владельца: сначала обсуждаем вопросы и дыры,
согласуем — и только потом делаем макет, а после макета — сам проект.
Технических решений (стек, схема БД, SMS-провайдер) здесь нет — они не
зафиксированы специально, до согласования.

Похожий разбор уже делался 31.08.2026 в сессии «Анализ реестра блогеров»
(план по дням, user-story, риски) — этот файл его не повторяет, только то,
что изменилось и что осталось открытым после сегодняшнего разговора.

## Спека — сжато, как есть в документе

- Цель недели: каталог на ~277 реальных карточек, блогер проходит полный цикл
  сам, админ ведёт базу без программиста, деплой с первого дня, мобильная
  вёрстка — приоритет.
- Петля: зарегался (инвайт → телефон → код) → загрузил скрин → данные легли в
  базу (модель читает скрин, пишет с пометкой «из скрина»).
- Поля карточки по спеке: ник · соцсети · подписчики (с флагом достоверности) ·
  тематика · район · язык · охват-ориентир · ставка · статус · телефон.
- Приёмка — один сценарий, один телефон, полностью с телефона.
- **Явно вне MVP по спеке:** SMS-шлюз — «казахстанский провайдер, договор и
  расход **заказчика**; до подключения коды выдаёт администратор».

## Расхождения между спекой и тем, что сказано 01.09

1. **SMS.** Спека: шлюз — забота и расход заказчика, вне MVP недели 1, коды
   выдаёт админ вручную. Даня 01.09: «подключим сервис провайдера sms,
   который через API будет отправлять коды» — это уже наша интеграция.
   **Открыто:** подключаем реально сейчас, или остаёмся на варианте спеки
   (ручная выдача) и настоящий SMS — задача заказчика на потом?
2. **Деплой.** Спека: рабочая ссылка с первого дня, всё остальное
   выкладывается на неё ежедневно. Даня 01.09: «Railway деплой в конце, после
   тестов». **Открыто:** сознательно уходим от ежедневного деплоя (тогда
   ближайший показ — макет на экране, не рабочая ссылка), или переносится на
   конец что-то более узкое — например, только финальный домен/аккаунт, а
   черновой деплой всё равно идёт с первого дня?

## Дыры — то, чего в спеке просто нет

3. **К6 — как подборщик связывается с выбранным блогером.** Телефон наружу не
   отдаём (это в спеке), способ связи не описан вообще. Варианты: ссылка на
   соцсеть блогера · заявка → администратору, который сводит стороны ·
   каталог закрытый, не для всех. **Дефолт не выбран, решать владельцу.**
4. **Реальные данные не такие, как ждёт спека.** Присланная таблица
   (Google Sheets, https://docs.google.com/spreadsheets/d/1-TmGoTnPQ4uuiIhjnIIuOis8dXBTbEKN9Ko5XTJdWrk)
   — это CRM переписки с блогерами: колонки «Дата, Блогер, Откуда, Встреча,
   Уточнение, Подписчики, Оплата, Пост-работа, Управление», 300+ строк, даты
   растянуты до октября (часть строк — планы на будущее, не готовые записи).
   Спека ждёт «нормализованную базу (277 записей)». Телефона отдельным полем
   нет — предположительно спрятан в «Оплата», разрежен. Полей «тематика»,
   «район», «язык» нет вообще. **Открыто:** кто сводит CRM к нормализованному
   виду — мы вручную/полуавтоматом, или заказчик даёт отдельный чистый файл?
5. **Оповещение участников.** Телефоны есть только у 30 из 277, приглашения
   рассылает заказчик своими каналами, порядок отдельно не согласован. Без
   канала для остальных 247 наполнение может не случиться — не в наших руках.
6. **Дизайн.** «Уже делается» на стороне заказчика, к старту макетов может не
   быть. Раз решили начинать со своего макета/концепта — вопрос снят, но
   стоит уточнить, пришлёт ли заказчик что-то раньше нашего показа.

## Что уже подтверждено

- Повторный вход блогера (старая дыра «Б7» из разбора 31.08) — решено: первая
  регистрация по инвайт-ссылке, дальше вход обычный — телефон + SMS-код. Это
  завязано на пункт 1 (SMS): если SMS не подключаем в эту неделю, повторный
  вход технически подтверждается тем же ручным кодом от админа.
- Личность блогера — телефон, один человек = одна запись (спека).
- Персональные данные — минимум на этом этапе: согласие при регистрации,
  телефон наружу не публикуется; полный контур ПД — вне этапа (спека).

## Термины простыми словами

- **Инвайт** — персональная ссылка-приглашение на конкретного блогера: открыл
  — увидел свою, уже частично заполненную карточку, а не пустую форму.
  Подтвердил телефон кодом один раз — это и есть регистрация. Дальше ссылка
  не нужна.
- **Подборщик** — третья роль, не блогер и не админ: человек заказчика (или
  его клиента), который листает публичный каталог и ищет блогера под
  рекламу — фильтрует по тематике, подписчикам, охвату. С этой ролью связана
  дыра К6 выше.

## Технический риск на заметку

В доме нигде нет готового кода или даже наброска для разбора скриншотов
моделью (vision) — ни в одном проекте. Узел придётся делать с нуля, самый
непроверенный кусок недели. Не блокирует обсуждение, но стоит знать заранее.

## Раунд 4 (02.09.2026) — SMS развернули, взяли готовый OTP-сервис

Слово владельца 02.09.2026 отменяет пункт 1 из «Продолжения разговора
01.09» («SMS — по спеке, провайдера не подключаем»). Теперь:

1. **SMS-оператора подключаем сразу**, через API. Ручная выдача кода
   админом остаётся только запасным путём (провайдер лёг / номер не
   принимает).
2. **Берём готовый OTP-сервис** — не свой код с нуля. Провайдер сам шлёт
   код, держит срок жизни, счётчик попыток, «отправить заново», сам
   регистрирует имя отправителя. У нас в коде — две команды:
   `otp.start(телефон)` и `otp.check(телефон, код)`.
3. **Аккаунта у заказчика нет.** Сначала тестируем на своём аккаунте
   (Twilio Verify — бесплатный старт, +7 поддерживает). Продакшн — аккаунт
   и оплата заказчика: либо тот же Twilio Verify, либо казахстанский
   **edna.kz OTP**, если юрист заказчика скажет держать телефоны в РК
   (закон о персональных данных и локализации). Обёртка в коде одна —
   смена провайдера = замена ключей, не переписывание.
4. **Телефон в форме подставляем** заранее из CRM тем ~30, у кого он есть;
   поле редактируемое.
5. **Повторный вход — без ссылки**, подтверждено: телефон + код, те же две
   команды OTP.

Что зафиксировано по цепочке входа (до окна карточки):

- **Экран 1 — переход по ссылке.** Токен в ссылке: случайный длинный,
  одноразовый, срок 30 дней, гаснет после регистрации, годен только на
  регистрацию. Плохой/просроченный/использованный → экран «ссылка
  недействительна, обратитесь к администратору».
- **Экран 2 — ввод кода.** Срок и попытки держит провайдер, мы показываем
  его ответ. «Отправить заново» с таймером.
- **Экран 3 — готово.** Создаём аккаунт блогера, гасим токен, ставим
  сессию, ведём на «Заполнить карточку». Сам экран карточки — следующий
  кусок, в этот не входит.
- **Что храним у себя:** телефон, ник, статус. Код у себя не храним — им
  владеет провайдер.

Макет трёх экранов (ссылка → номер → код, до окна карточки) —
`https://claude.ai/code/artifact/423dd6db-0c9e-4259-980e-de8796915585`.
Формальное решение дома по развороту SMS — записать через `reshenie`.
